# Harness research, 2026-10-31

This report covers what else to improve in the orchestration plugin. It draws on four research passes and two live probes on Claude Code 2.1.316:
- Claude Code docs and changelog up to 2.1.316;
- other agent harnesses;
- the literature on reading documents and on routing between models;
- this plugin's own logs and benchmarks.

Every claim carries a tag:

- **verified**: probed live in this session.
- **doc**: official Anthropic docs.
- **data**: this repository's logs or benchmarks.
- **lit**: a paper or benchmark.
- **secondary**: a third-party source that was not confirmed against a primary one.

Part 2 (section 6) adds five more passes, after the 0.4.0 proposal:
- the Claude Code changelog 2.1.250–2.1.300, agent teams, plugin features and Anthropic's official plugins;
- community Claude Code orchestrators;
- research and production harnesses;
- review precision, verification, eval method and agent security;
- an audit of this plugin's own prompts.

## Final verdict

**1. The core design holds.** The most popular community systems run the same loop as this plugin: a plan, a fresh subagent per task, review between tasks, and tests.
- Those systems are obra/superpowers (309,732 stars), GitHub spec-kit (144,182), ruflo (80,367), BMAD-METHOD (54,806) and oh-my-claudecode (40,444).
- They enforce the loop with prompts and skills; this plugin enforces it with hooks.
- None of them publishes a measured result.
- Nothing found argues for more agents, swarms or memory systems.

**2. The gaps are measurement, review precision, security and cost:**
- **Measurement.** There is no cost per role and no log of reads, and with 1–2 runs per arm the benchmark can show only differences of tens of points.
- **Review precision.** 29% of reviews fail, and every failure costs a full implementer retry. Anthropic's own review plugins report only findings with a confidence of 80 or more, and run a separate check on each finding before keeping it (6.2).
- **Security.** The reviewer holds the "lethal trifecta": it reads untrusted content, can see private data, and can send data out (6.5). The researcher's Bash limits are not enforced (3, item 4).
- **Cost.** The reading model ignores what is being read (section 2).

**3. Recommended releases.**

0.5.0, "review precision and verification". Slices get planned when it starts.
- Each reviewer gap carries a confidence from 0 to 100, and only gaps of 80 or more fail a slice.
- Before a retry, a short check tries to refute each gap against the diff.
- An exclusion list for reviewers: problems that predate the slice, anything a linter catches, nitpicks, style.
- Bug-fix slices write a failing reproduction test first, and the test gate checks it goes from failing to passing.
- The tests run once when a run opens, so failures that were already there are known.
- A stall gate (`replan_required`): two failing reviews with the same gap, or three in total, block until a replan runs.
- A PostCompact hook puts the open run's plan back into the orchestrator after compaction.
- `userConfig` replaces the `ORCH_*` environment variables.
- The nudge warns when agent teams are switched on.
- The reading router also covers workflow agents, through the dashboard mod's `agent.spawn` hook (after a probe).

**Bench track, alongside both releases:**
- Grow the evals to 20–50 tasks drawn from real failures.
- Run at least 5 runs per arm on the same tasks, and compare arms task by task.
- Report standard errors grouped by task.
- Measure the gates by how often they get every run right (pass^k).
- Only then call any of H10–H16 supported.

**Experiments, run in the bench before adopting:**
- best-of-N on RISKY slices;
- an opus reviewer at low effort against the sonnet one;
- a second reviewer on a different model;
- a lessons file carried between runs.

**Not doing:** swarms and hive-minds, agent catalogues of 200 entries, GUIs for managing sessions, Taskmaster, Ralph loops without gates, agent teams for now, best-of-N on every slice, trained routers, an architect/editor split, Haiku implementers, and bench tasks taken from SWE-bench Verified.

## 2. Choosing the reading model by file type

### 2.1 Why it pays

Model prices and limits (**doc**, claude-api skill model table, cached 2026-10-06):

| Model | Input $/MTok | Output $/MTok | Reads PDFs and images |
|---|---|---|---|
| Haiku 5.5 | 0.10 for prompts up to 100K tokens, 0.50 above | 0.50 (2.50 above 100K) | yes |
| Sonnet 5.5 | 2 | 10 | yes |
| Opus 5.5 | 4 | 20 | yes |
| Fable 5.1 | 10 | 50 | yes |

All four have a 1M context window. Support for PDFs and images comes from the supported-model lists on the PDF support and vision pages (**doc**).

**What a PDF page costs.** Sent as a PDF, each page costs its extracted text (1,500–3,000 tokens) plus a page image. The image costs ceil(w/28) × ceil(h/28) tokens, capped at 1,568 on the standard tier and 4,784 on the high-resolution tier (models from 4.7 on). Sent as extracted text, the same page costs only the 1,500–3,000 (**doc**, pdf-support and vision).

**Worked example**, assuming about 3k image tokens and 2k text tokens per page:

| 40-page text PDF | Tokens | Input cost |
|---|---|---|
| Read as a PDF by Opus | about 200k | about $0.80 |
| Read as text by Sonnet | about 80k | about $0.16 |
| Read as text by Haiku | about 80k to 104k | about $0.008 to $0.05 |

Token counts depend on each model's tokenizer. Haiku 5.5's newer tokenizer counts about 30% more tokens than Haiku 4.5 (**doc**, `shared/models.md`). If the 80k becomes about 104k, it crosses Haiku's 100K price step and costs about $0.05. Even then it is at least 15 times cheaper than Opus reading the PDF. On a subscription the saving shows up as usage-limit headroom instead of dollars.

**Anthropic's cost guidance** (**doc**, claude-api skill, `shared/cost-optimization.md` §2.6–2.7) supports this:
- The smallest model fits "high-volume work with checkable outputs, not long agentic loops".
- Deciding when to call a stronger model needs a cheap signal: "asking the executor to recognize the hard cases itself demands the very judgment it's missing".
- "Re-run failures at higher effort" kept the pass rate of running everything at the higher setting, for a little over half the cost, where a failure signal exists.
- "Price the tail, not the median."

Reading to extract facts is high-volume, checkable work. File properties are a cheap signal that does not ask the model to judge itself.

**The routing literature (lit):**
- RouteLLM cut cost by 35–85% while keeping 95% of GPT-4 quality on MT Bench, MMLU and GSM8K.
- Hybrid LLM made up to 40% fewer large-model calls with no quality drop.
- AutoMix cut cost by more than 50%, though the paper notes its self-verification signal is noisy.

None of these was measured on reading documents, and none accounts for cache effects.

**Where cheap readers fail (lit):**
- Tables: table scores range from 58 to 83 TEDS across tools (OmniDocBench).
- Handwriting and scans: pipeline extractors fail, and vision models do much better (OmniDocBench).
- Long documents that need reasoning across pages: the best model scores 44.9 F1 (MMLongBench-Doc).

Extracting clean prose is easy. No published comparison of Claude tiers on documents exists, so the plugin has to measure this itself (2.6).

**Nobody does this yet.** No surveyed harness picks a model by file type (secondary). Some tools convert files first: MarkItDown converts PDF and xlsx to Markdown, and doc2md-helper sends text PDFs and scans to different parsers.

### 2.2 Tiers

These thresholds are initial guesses, to be calibrated by the eval in 2.6. No source gives them.

A read's tier is the higher of its file tier and its question tier, raised to opus when the slice is RISKY.

**File tier**, from a profiler (`file-profile.mjs`) that makes no model call:

| File | Signal | Tier | How it is read |
|---|---|---|---|
| `.txt` `.md` `.json` `.csv` `.log`, source code | extension, size | haiku | as is |
| PDF with a text layer, no tables or figures | `pdfinfo` page count; `pdftotext` gives about 500 or more characters per page; `pdfimages` finds few images; no column pattern | haiku | text converted in advance and cached |
| PDF with tables or several columns | runs of aligned columns in `pdftotext -layout` output | sonnet | PDF pages (Read with `pages`) |
| Scanned PDF, or a weak text layer | under about 100 characters per page | sonnet | PDF pages |
| PDF whose charts or figures must be read for numbers | many or large images from `pdfimages -list` | sonnet; opus when the numbers drive a decision | PDF pages |
| `.xlsx` | sheet count, `<f>` formula count, merged cells | haiku for plain data (exported as CSV); sonnet when there are formulas | |
| `.docx` `.pptx` | text from the XML; image count | haiku; sonnet when image-heavy | |
| Image | dimensions only (the content cannot be judged without a model) | sonnet by default | |
| Long document with a question that spans pages | about 50 pages or more and READ: judge | opus, whole document, no page split | |

Handwriting cannot be detected cheaply. It falls under "scanned", so it never goes to haiku.

**Question tier**, from a new brief line `READ: lookup | extract | judge`:
- lookup and extract go to haiku;
- judge (compare, assess, decide) goes to sonnet;
- a RISKY slice goes to opus.

### 2.3 Enforcement, verified live

**verified**: a PreToolUse hook on the Agent tool can change a subagent's model by returning `updatedInput` with a `model` field.

The probe ran on 2.1.316 in a scratch project, with an agent `probe` whose frontmatter says `model: opus`:
- Without the hook, the subagent ran `claude-opus-5-5`.
- With a hook that sets `model: "haiku"`, it ran `claude-haiku-5-5`.

The model was read from the subagent's transcript at SubagentStop. The hooks doc lists `model` among the Agent tool's inputs but does not say `updatedInput` works for Agent (**doc**). The probe settles it for this version.

Model precedence (**doc**, sub-agents): per-call `model` > frontmatter `model` > `CLAUDE_CODE_SUBAGENT_MODEL` > the main model. `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` overrides all of them. The per-call `model` accepts only the aliases `sonnet`, `opus`, `haiku` and `fable`.

**Design:**
- **One hook decides.** Put the routing inside `plan-check.mjs`, which is already the only PreToolUse gate on Agent. That one hook then either blocks (exit 2) or rewrites, which avoids two hooks giving different answers on the same launch.
- **New brief lines.** Researcher briefs gain `SOURCES: <paths or URLs>` and `READ:`. Per the one-parser rule, that means changing `brief.mjs`, `docs/brief-grammar.md`, the dashboard mirror and the fixtures together.
- **When the router acts.** It picks a model only when the brief names sources. It may raise a model the orchestrator chose explicitly, but never lower it.
- **Logging.** Every decision is logged with its signals, and the dashboard pane shows how many reads went to each tier.
- **Opt-in at first.** It ships behind `ORCH_READ_ROUTER=on` until H14 (2.6) is measured.

**Caveat.** `updatedInput` takes effect only together with `permissionDecision: "allow"` or `"ask"`, and "ask" cannot be answered in a headless run.
- "allow" auto-approves the launch, so the router must rewrite only launches that would pass anyway: project and plugin agents, never built-ins.
- A hook's "allow" does not override a `permissions.deny` rule. The hooks doc says deny rules "are still evaluated, so a hook returning allow doesn't override a matching deny rule" (**doc**). The blocked built-ins stay blocked.

**Fallback without the hook.** The orchestrator can pass the per-call `model` and `effort` itself; per-call `effort` exists since 2.1.292 (**doc**). This works only as far as the orchestrator follows its prompt.

### 2.4 Convert first

- **Convert text PDFs.** Run `pdftotext` (poppler is installed here; the Read tool already uses poppler's `pdftoppm` for PDFs over 10 pages, **doc**). Cache the result in the state directory, keyed by the file's hash.
- **What the reader gets.** It is handed the text file and a page map. Pages flagged as hard (tables, scans, figures) are listed for a stronger tier to read as PDF pages.
- **Split only for extraction.** Split documents by page only to extract facts. A judge question that spans pages stays on one strong reader with the whole document, since MMLongBench-Doc shows cross-page reasoning is the hard part.

### 2.5 Check, then escalate

- **Quotes.** Readers return verbatim quotes with locators (`file:line`, or the file and a page number).
- **The check.** A SubagentStop check searches for each quote in the source text: the cached text file, or the file itself.
- **Escalation.** When a quote is not found, or OPEN is not empty, the orchestrator re-runs that read one tier up. This is Anthropic's "re-run failures at higher effort" pattern, with a check that does not depend on the model's own confidence (AutoMix found self-verification noisy).
- **Limit.** The check catches invented quotes. It cannot check a number read from a scan, which has no text layer, so scans never go to haiku.

### 2.6 Measure before trusting it

1. **Log reads first** (section 3, item 1) and collect about two weeks of real use: which file types, which agents, how many tokens.
2. **Bench task `d2-docs`.** A small corpus with known answers:
   - a txt file and a text PDF;
   - a PDF with tables and a scanned PDF;
   - an xlsx with formulas and a chart image;
   - a 60-page document with a question that spans pages.

   Three arms: researcher on haiku for everything (today), on sonnet for everything, and routed. Metrics: answer accuracy, reading tokens and wall time. Price the hardest tenth separately.
3. **H14 (proposed).** Routed reading stays within 2 points of the all-sonnet arm's accuracy using at most half of its reading tokens, and beats the all-haiku arm on tables and scans.

### 2.7 Risks

- **A hard page sent to the wrong tier.** Haiku could quietly misread a table. Mitigations: conservative signals (any table or figure goes to sonnet), the quote check, and never sending scans to haiku.
- **Wasted calls.** An escalation pays for the cheap read and the strong one. It also adds latency.
- **Caches are scoped to one model.** Little is lost here, because subagents already have their own contexts.
- **Thresholds.** They are uncalibrated until 2.6 runs.
- **No poppler on another machine.** Then fall back to tiers by extension only, with no conversion.

## 3. Other improvements, ranked

Each item gives the evidence, what Claude Code ships natively and a rough size.

1. **Telemetry v2: tokens, turns, model and reads per agent.**
   - *Evidence:* no split by role exists anywhere. Launch records log the model on 41 of 850 launches, reads are not logged, and maxTurns hits cannot be detected (**data**). Token usage explained 80% of the performance variance in Anthropic's research system (**doc**).
   - *Approach:* read usage from the subagent transcripts at SubagentStop, since they record real token usage from 2.1.307. Do not use the Agent PostToolUse `totalTokens`, which covers only the final request (**doc**). Log the model on every launch, and add a PostToolUse `Read` logger that records the agent, path, extension and size, never contents.
   - *Native:* `/cost` and OTel give session totals, not totals per slice or per role.
   - *Size:* S–M.
2. **Reading by file type (section 2).** Size: M.
3. **Check the workflow's plan.**
   - *Evidence:* the planner prompt asks for disjoint files, but no code checks it. A misspelled `dependsOn` id is treated as a cycle, and the slices still waiting then run in one wave (`orchestrate.js:243-246`). Native workflows have no plan check either.
   - *Approach:* after `plan:slices`, reject overlapping files and unknown `dependsOn` ids and ask the planner once more. Add a reviewer pass on the plan, as the native path has.
   - *Size:* S.
4. **Enforce the read-only roles.**
   - *Evidence:* **verified** in this session. The researcher's tools are Read, Grep, Glob and Bash limited to `git`, `wc`, `ls` and `du` patterns, yet in auto mode it wrote a Python file with a heredoc and ran `python3`. The Bash patterns in `tools` did not restrict it.
   - *Approach:* add a PreToolUse Bash rule for `agent_type` researcher that allows only the listed prefixes and denies redirection and interpreters. PreToolUse input from a subagent carries `agent_type` (**doc**, hooks).
   - *Size:* S.
5. **Escalate the implementer on its last attempt.**
   - *Evidence:* "re-run failures at higher effort" held the pass rate for a little over half the cost of running everything higher (**doc**). 17 of 129 slices ended failed (**data**, mostly before 0.2.0).
   - *Approach:* run attempt 3 as a fresh implementer with `model: "opus"` (or per-call `effort: "high"`) plus the gaps, instead of a third sonnet try. A SendMessage resume keeps the original model, so the escalated attempt has to be a new agent.
   - *Size:* S.
6. **Raise implementer maxTurns from 40 to 80.**
   - *Evidence:* 4 hits in this session. Since 2.1.246, a maxTurns stop returns partial output that can be resumed (**doc**).
   - *Approach:* edit `src/config.ts`, then run `npm run sync-agents`.
   - *Size:* trivial.
7. **Worktrees from HEAD wherever the session started.**
   - *Evidence:* every implementer in this session had to run a fast-forward merge first, because the repo's `worktree.baseRef` did not load from `~`.
   - *Approach:* either a `WorktreeCreate` hook (the event is in the hooks doc; how it behaves needs a probe), or docs telling users to set `worktree.baseRef` in `~/.claude/settings.json`.
   - *Size:* S.
8. **Workflow cost settings.**
   - *Evidence:* W-mix was the slowest arm.
   - *Approach:* set `subagentPromptCacheTtl: 1h` for fan-outs and `workflowSizeGuideline` (**doc**), then measure.
   - *Size:* trivial.
9. **Effort per call by slice size.**
   - *Evidence:* per-call `effort` exists from 2.1.292 and `CLAUDE_CODE_SUBAGENT_EFFORT` from 2.1.316 (**doc**). In Anthropic's runs, research effort curves were nearly flat (low gave up a few points for a third to a half off the cost) and coding was a real tradeoff (**doc**).
   - *Approach:* run an effort sweep in the bench before changing any default.
   - *Size:* M (bench time).
10. **A test gate for code with no test command.**
    - *Evidence:* 259 `no_test_command` decisions (**data**). Many are prose work, where skipping is right, so split those out first.
    - *Approach:* run the slice's acceptance command from the brief when no test command is detected.
    - *Size:* S.
11. **Review by a different tier, as an experiment.**
    - *Evidence:* the reviewer and the implementer are both sonnet. A judge favours its own outputs more the better it recognises them (**lit**, arXiv 2404.13076).
    - *Approach:* bench an opus reviewer at low effort against the sonnet reviewer at medium.
    - *Size:* bench only.
12. **Keep worker contexts small.**
    - The researcher and integrator already set `omitClaudeMd: true` (`.claude/agents/researcher.md:7`, `integrator.md:7`).
    - *Approach:* set `autoCompactWindow` (2.1.296) for long implementers (**doc**), then measure.
    - *Size:* S.

**New hook events worth a look (doc):**
- `StopFailure`: API errors at stop, so the gate stops misreading them.
- `PostCompact`, `TaskCreated` / `TaskCompleted`.
- `PreModelSwitch` / `PostModelSwitch`.
- `WorktreeCreate` / `WorktreeRemove`.

## 4. Considered and not recommended

- **Learned routers (RouteLLM, FrugalGPT).** They need labelled traffic. This plugin has about 850 launches in two weeks and routes per agent, not per prompt. Start with rules and measurement.
- **An architect/editor split inside the implementer (Aider).** Aider's gains of 3–5 points came from models that were weak at its edit formats (**lit**, aider.chat). Claude Code edits with tools, and the plugin already splits planning (opus) from editing (sonnet).
- **Haiku implementers.** Anthropic says the smallest model fits checkable bulk work, not long agentic loops (**doc**).
- **The advisor tool.** It is API-only, and on Anthropic's coding benchmark it scored about where the executor model's own effort curve did (**doc**).
- **Splitting a document by page for questions that span pages.** That breaks exactly the reasoning the hardest benchmark measures (**lit**).
- **A Copilot-style automatic model for every agent.** No published quality numbers (**secondary**).

## 6. Part 2: how others build it, and what to take

### 6.1 Where the plugin stands

- **Same loop, weaker enforcement.** Community systems run the same loop as this plugin: a plan, a fresh subagent per task, review between tasks, and tests.
  - Star counts and release dates come from the GitHub API on 2026-10-31 (**data**). Mechanisms come from each project's README (**secondary**).
  - superpowers adds a TDD skill, worktrees with a check for a clean test baseline, and code review between tasks that blocks on critical issues.
  - spec-kit chains constitution, specify, plan, tasks and implement, then repeats implement and converge until converge reports "Converged".
  - oh-my-claudecode runs a team pipeline (plan, PRD, exec, verify, fix) and asks other CLIs for review.
- **No measurements anywhere.** None of these projects publishes a measured result. This plugin, with its benchmark, is unusual in having any.
- **Review precision.** Anthropic's official review plugins go further than this one (6.2).
- **What research systems back with numbers.** Systems that publish numbers support three things the plugin lacks: a verifier that picks among attempts, reproduction tests, and condensed context (6.3, 6.4).

### 6.2 Review precision: the biggest gap found

**What others do:**
- **Anthropic code-review plugin** (**doc**, github.com/anthropics/claude-plugins-official, `plugins/code-review/commands/code-review.md`):
  - Haiku decides whether to skip.
  - 4 reviewers run in parallel: 2 Sonnet for CLAUDE.md rules, 2 Opus for bugs.
  - One validation subagent then checks each flagged issue, and issues that fail validation are dropped.
  - Exclusions: problems that predate the change, anything a linter catches, nitpicks, and anything uncertain.
- **pr-review-toolkit:** its code reviewer scores each issue from 0 to 100 and reports only scores of 80 or more (**doc**, `plugins/pr-review-toolkit/agents/code-reviewer.md`).
- **Anthropic's managed Code Review:** a verification pass tries to disprove each finding, and under 1% of posted findings were marked incorrect (**secondary**).
- **Cursor Bugbot:** started with 8 parallel passes, kept findings the passes agreed on, then ran validators. The share of findings authors fixed went from 52% to over 70% (**secondary**, a snippet of the primary page).

**This plugin today:** 29% of reviewer replies fail, and each failure sends a sonnet implementer back. A false failure therefore costs a whole retry, and some slices went through 4–5 failing reviews (**data**).

**Take:**
1. Every gap in a reviewer reply carries a confidence from 0 to 100, and only gaps of 80 or more fail the slice. This needs a new reply line in `brief.mjs`, the dashboard mirror and the fixtures.
2. Before a retry, a short validation review tries to refute each gap against the diff. Refuted gaps are dropped.
3. Add the exclusion list and "skip style" to `reviewer.md`.

### 6.3 Verification with measured gains

**Evidence:**
- **Reproduction tests:**
  - Tests generated from the issue and used to filter candidate fixes doubled SWE-agent's precision (**lit**, SWT-Bench, arXiv 2406.12952).
  - Agentless picks a reproduction test by running it on the original code, then uses it to choose a patch (**lit**).
- **A verifier choosing among attempts:** best-of-5 with a trained critic raised SWE-bench Verified from 60.6% to 66.4% (OpenHands, primary blog).
- **Run tests and retry:** executable feedback with up to 3 retries added 4.2 and 5.4 points (**lit**, MetaGPT). The plugin already does this: the implementer runs its acceptance check, and the test gate follows.
- **Interface design:** in SWE-agent, rejecting edits that fail the linter was worth 3 points, and collapsing old observations scored 18.0% against 15.0% with full history (**lit**).
- **A clean test baseline:** superpowers checks for one before work starts (**secondary**).

**Take:**
1. **Reproduce first on bug fixes.** A brief line `KIND: bugfix` makes the implementer add a failing test first, and the test gate records it failing before the fix and passing after.
2. **A test baseline when a run opens.** Failures that were already there are then neither blamed on implementers nor raised by reviewers, which pairs with the exclusion list.
3. **Best-of-N only on RISKY slices,** as a bench experiment: it multiplies the cost by N.

### 6.4 Context and state

**What others do:**
- **Magentic-One** (**lit**, arXiv 2411.04468):
  - A Task Ledger: verified facts, facts to look up, guesses and the plan.
  - A Progress Ledger, answered every turn.
  - A stall counter that triggers reflection and a new plan once it passes 2.
  - GAIA score: 32–38%.

  This plugin's replan rule ("two reviews with the same gap") exists only in the prompt.
- **Condensing context:**
  - OpenHands' condenser halves the cost per turn at about the same solve rate, 54% against 53% (primary blog).
  - Factory scored compressed contexts by asking probe questions. Structured summaries (intent, file changes, decisions, next steps) scored 3.70, against 3.44 for Anthropic's. The record of which files changed scored worst for every method (primary, vendor).
- **Manus:** the KV-cache hit rate is the key cost metric. Keep prefixes stable and contexts append-only, keep errors in context, and restate the goal at the end (primary, no evaluation).
- **Cognition:** don't split decisions or parallel code-writing across agents without shared context (primary, no numbers). This agrees with the plugin's disjoint-files rule.
- **Anthropic:** subagents should return summaries of 1–2k tokens (**doc**, the context engineering post).

**Take:**
1. **A stall gate.** The review gate counts failing reviews per slice. At two with the same gap, or three in total, it blocks with `replan_required` until a REPLAN plan review runs. This turns the prompt rule into a gate.
2. **A file trail recorded by code.** Record each slice's changed files at SubagentStop from git, not from the model's reply.
3. **Re-inject the plan after compaction.** A PostCompact hook puts the open run's plan and constraints ledger back into the orchestrator. superpowers has a post-compaction hook, and the PostCompact event exists (**doc**).

### 6.5 Security

**Background:**
- **Willison's lethal trifecta** is private data, untrusted content and outward communication in one agent (primary).
- **Meta's Rule of Two:** an agent should hold at most two of untrusted input, sensitive access and the power to change state (**secondary**).
- **This plugin's roles:**
  - The reviewer holds all three: web pages and diffs, the repository, and Bash plus web fetch.
  - The researcher reads the web and the repository, and its Bash limits are not enforced (**verified**, section 3, item 4).
- **Auto mode:**
  - Its input probe only warns about tool outputs, and an outside researcher reports injections succeeding 60–80% of the time (primary and **secondary**).
  - In this session, auto mode's review of subagent reports flagged one research report for text shaped like an instruction. It was a changelog line about `bypassPermissions`, and no instruction was present.
  - The native layer helps, but it is not a boundary.
- **Claude Code sandboxing:** isolating the filesystem and network cut permission prompts by 84% (primary).

**Take:**
1. **Narrow the reviewer's web access; don't remove it.** Non-code reviews have to check each claim against its cited source with WebFetch (`reviewer.md:15`), and the reviewer has no Agent tool to hand that job to a researcher.
   - A reviewer egress guard (PreToolUse on WebFetch for `agent_type` reviewer) allows only URLs named in the brief or in the files under review, so an injected instruction cannot send data to a URL it chose.
   - Bash can still reach the network until take 3 is in place, so this narrows the trifecta without closing it.
2. The researcher Bash guard (section 3, item 4).
3. Recommend sandboxing, with a network allowlist, for implementer and reviewer Bash.
4. Put `onFailure: "block"` on the Bash judge (2.1.295, **verified** in the raw changelog), so a crash or timeout denies the command. Keep the other gates fail-open: a crashing plan check that blocked every launch would wedge the session.

### 6.8 How to measure

- **Anthropic's eval guidance** (**doc**):
  - Start with 20–50 tasks drawn from real failures.
  - Prefer code graders, grade outcomes, and read transcripts.
  - Measure reliability with pass^k, the chance that all k runs pass: 0.75³ ≈ 42%.
- **Error bars.** Report the standard error grouped by task, and compare arms task by task (**lit**, arXiv 2411.00640).
- **Sample size:**
  - For a pass/fail metric, detecting a 5-point difference at 80% power takes about 1,000–1,600 runs per arm when the arms run on different tasks. That is standard two-proportion arithmetic.
  - Running both arms on the same tasks cuts that by a factor of about (1 − the correlation between arms).
  - The bench scores the fraction of hidden tests passed, not pass/fail, so its variance is lower.
  - Even so, with 1–2 runs per arm only differences of tens of points mean anything.
  - The "direction only" label in the docs is right, and H10–H14 need repeated runs on the same tasks before any is called supported.
- **Avoid SWE-bench Verified for tasks.** OpenAI found flawed tests in at least 59.4% of an audited hard subset, plus contamination (primary).

### 6.9 Not worth taking

- **ruflo swarms, hive-mind and federation:** big claims, no measurements, and a lot to own.
- **Catalogues of 200 agents (wshobson) and frameworks with 30 commands (SuperClaude):** breadth, not gating.
- **GUIs for managing sessions** (Claude Squad, vibe-kanban, Crystal, Conductor): they help a person juggle sessions; they don't make results more correct.
- **Taskmaster:** stalled since April 2026, and it overlaps the plan.
- **Ralph loops without gates:** no independent review. Only the idea of a `passes` flag per task is useful, and the journal already provides that.
- **Agent teams for now:** experimental and interactive-only.
- **Best-of-N on every slice:** it multiplies the cost by N.
