# Maintainer notes

What each release added to the rules of this repository, moved whole and in order out of `CLAUDE.md`, which every session loads on every turn. This file is not loaded automatically: read it before changing hooks, gates, the plugin build, the Bash judge, the headless scripts or the release process. The standing rules found here are listed, one line each, in `CLAUDE.md` under "Standing rules from the release notes"; `CHANGELOG.md` has each release in full. The text below is unchanged from `CLAUDE.md`, so "above" and "below" in it point at the neighbouring notes here, and "the model policy above" means the model policy in `CLAUDE.md`, Rules.

## 0.4.0: lines and gates

- 0.4.0 lines and gates. Briefs may carry `SOURCES:`/`READ:` (researchers), `KIND: bugfix` (implementers: failing reproduction test first) and `VALIDATE: gaps` (a reviewer re-checks another review's gaps before a retry); replies may carry `GAP: <0-100> <text>` (reviewers) and `QUOTE: <locator> | <verbatim text>` (researchers). New hooks: `read-log.mjs`, `researcher-guard.mjs`, `egress-guard.mjs`, `compact-context.mjs`, `quote-check.mjs`, and the read router in `plan-check.mjs` (profiles files with `file-profile.mjs`; `plan-check.mjs` is the only hook that ever returns an allow). The stall gate (`replan_required`) is native-only. Switches: `ORCH_GAP_MIN` (default 80), `ORCH_STALL_GATE`, `ORCH_GUARDS`, `ORCH_READ_ROUTER` (opt-in), `ORCH_QUOTE_CHECK`, `ORCH_BASELINE` (test baseline: `inform` by default, failing tests still block and the message marks failures that also fail on the base as probably pre-existing; `allow`, opt-in and heuristic, allows when every qualified failure also fails on the base; `off`), `ORCH_BUGFIX_CHECK`; each also reads the plugin's `userConfig` value (`CLAUDE_PLUGIN_OPTION_<KEY>`), the environment winning. Test gate time (1.4.0, environment only, no plugin setting): `ORCH_TEST_TIMEOUT_S` (the test run, default 600; a suite that hangs gets SIGTERM with its children, SIGKILL 5 s later, and blocks as `tests_failed` with `timed_out` and `limit_s` whatever status it exits with) and `ORCH_HOOK_BUDGET_S` (the whole `verify.sh`; default and maximum min(870, Claude Code's stall limit `CLAUDE_ASYNC_AGENT_STALL_TIMEOUT_MS` in seconds - 60), so 540 by default: a hook killed at its 900 s timeout does not block, and a subagent with no progress for the stall limit is ended while its gate runs); one suite at a time per project: the test run and the base run or bugfix check after it hold `test-gate.lock` in the state dir, the wait counts against the budget, and an isolated gate whose wait reaches its floor logs `tests_failed_isolated` with `not_run` (a doubt signal) while the shared tree runs without the lock; the base run and the bugfix check get only the time left (each base run at most `ORCH_BASE_TIMEOUT_S`), and a bugfix check that runs out blocks with `bugfix_timeout`; one whose temp folder was removed mid-run blocks with `bugfix_tmp_lost` (1.4.2; both under the bugfix cap). Also environment only (1.4.2): `ORCH_TURN_WARNING=off` (the turn warning, `turn-budget.mjs`, PostToolUse: once per agent, at 80% of maxTurns, tells our own worker to commit and report; never blocks) and `ORCH_SOURCES_NOTE=off` (the plan check's coverage note for a researcher whose SOURCES name two or more local files). The plan check blocks an isolated implementer launch with `worktree_base_not_head` when the effective `worktree.baseRef` is not `"head"` and HEAD differs from `origin/HEAD` (two blocks per slice, then it gives up). FILES globs (1.4.2): `*` within one segment, `**` across segments, `?` one character; a planned glob covers only what it matches, two entries overlap when some path could match both, and `file_overlap` compares normalised paths. Path identity (1.4.3): `file_overlap` and `not_in_plan` resolve each entry's fixed leading folders through symlinks and case-fold them on a case-insensitive file system, and a glob's first wildcard segment (not `**`, not the last) also stands for the symlinked folders it matches, up to 32; what cannot be decided overlaps. Since 2.0.0 `file_overlap` also reads a symlink reached through `**` or a later wildcard, hard links and the Unicode NFC/NFD forms of one name; out of reach: a link or hard link made after the launch, a hard link whose other name lies outside every entry's walk, and those names in `not_in_plan`. `ORCH_READ_ROUTER_BUDGET_MS` is capped at 40000, and a SOURCES symlink leading outside the project is tiered by extension, never read or cached. The egress guard also takes hosts from the coordinator's resume message to a reviewer (a user record with `isMeta`, `origin.kind` `coordinator` and string content), never from any other later record; with no readable brief it falls back to the reviewer's launch record (`urls`, host-shaped `sources`, its slice's planned FILES). The researcher guard allows exactly `2>/dev/null` and `2>&1` as stderr redirections, nothing else. Name switches only in maintainer text, never in agent bodies, skills or the nudge's context. Run implementer and reviewer Bash in Claude Code's sandbox with a network allowlist: the guards are not a boundary. Details in `.claude/rules/agents.md`.

## 0.4.0 addendum: skill selection

- Skill selection (0.4.0 addendum). Implementer, researcher and reviewer briefs (never the integrator's) may carry `SKILLS: <comma-separated skill names>`, written by the orchestrator when a slice clearly needs an installed skill, named as the Skill tool lists it; workers load each with the Skill tool before starting and ignore one that does not fit (saying so in one line of the report, not under OPEN: a non-empty OPEN is a doubt signal). `plan-check.mjs` also appends a suggestion block to those launches: at most 3 installed skills (1 for reviewers), names and reason codes only, picked from FILES/SOURCES file types, the role and the goal's words, out of the skills found on disk (`~/.claude/skills`, with `synced/<uuid>/<name>` named `anthropic-skills:<name>`; the project's `.claude/skills`; enabled plugins' skills). Researcher and reviewer have the `Skill` tool, the integrator does not. The plan check's allow widens: it may return `updatedInput` with allow for this plugin's implementer (only when its rules allow with `ok` or `light_path`), researcher and reviewer, combining the read router's model change and the hint text in one `updatedInput`; never for built-ins or fork, never lowering a model.

## 1.4.0

- 1.4.0: skills in the orchestrator ( `docs/skills.md`). The orchestrator has the `Skill` tool and loads at most two plan-shaping skills per run; a reviewer gets up to 2 suggestions when its launch runs on opus or above (1 otherwise). A run may draft one skill as a `KIND: skill` implementer slice in a git worktree of the private skills repository (public only with `TARGET: public`), on branch `skill/<name>`. Switches: `ORCH_SKILL_CREATE` (`off` blocks skill slices), `ORCH_SKILLS_REPO_PRIVATE`, `ORCH_SKILLS_REPO_PUBLIC` (userConfig `skill_create`, `skills_repo_private`, `skills_repo_public`; 20 plugin settings then, 21 since 1.6.0). The plan check's single allow now also carries the skill facts and the DRAFTS lines, for our own implementer, researcher and reviewer only. The skill gate (`skill-gate.mjs`, deny-only) checks the draft at the implementer's stop, including its seal (`skill-seal.mjs`, `provenance.json`), every line the branch's commits add and every path they touch, and since 2.0.0 the raw commit and tag objects (`skill-scan.mjs`, shared with `npm run skill-publish`). No agent or hook pushes or installs a skill: `npm run skill-publish` (`scripts/skill-publish.mjs`), run by a person, pushes, opens the pull request and, with `--merge`, installs. Workers report `SKILLS-USED:`/`SKILLS-SKIPPED:`; the journal keeps them and `npm run report` has a Skills section. Details in `.claude/rules/agents.md`. The dashboard pane is off by default in every terminal (herdr included) until `/orchestration on`; its hooks catch their own errors, so they never fail the event they wrap (`docs/dashboard.md`).
