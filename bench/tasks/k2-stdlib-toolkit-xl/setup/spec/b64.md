# toolkit.b64

A pure-Python binary-to-text codec module in `toolkit/b64.py` that behaves
like the Python 3.13 standard library module `base64` for the subset below.
The hidden tests run the same call on `toolkit.b64` and on `base64` and
compare the results. The solution may not import `base64` or `binascii`, or
any other module on the blocked list in SPEC.md.

## API

All functions return `bytes`. Keyword arguments are passed by keyword in
the tests.

- `Error`: exception class, a subclass of `ValueError`. Raise it wherever
  `base64` raises `binascii.Error`. Where `base64` raises a plain
  `ValueError` (named below), raise `ValueError` itself (not `Error`).
- Base64: `b64encode(s, altchars=None)`, `b64decode(s, altchars=None, validate=False)`,
  `standard_b64encode(s)`, `standard_b64decode(s)`, `urlsafe_b64encode(s)`,
  `urlsafe_b64decode(s)`, `encodebytes(s)`, `decodebytes(s)`.
- Base32: `b32encode(s)`, `b32decode(s, casefold=False, map01=None)`,
  `b32hexencode(s)`, `b32hexdecode(s, casefold=False)`.
- Base16: `b16encode(s)`, `b16decode(s, casefold=False)`.
- Ascii85: `a85encode(b, *, foldspaces=False, wrapcol=0, pad=False, adobe=False)`,
  `a85decode(b, *, foldspaces=False, adobe=False, ignorechars=b' \t\n\r\v')`.
- Base85: `b85encode(b, pad=False)`, `b85decode(b)`.
- Z85: `z85encode(s)`, `z85decode(s)`.

## Argument types

- "Bytes-like" means `bytes`, `bytearray` or a `memoryview` of bytes.
- Encoders (`b64encode`, `standard_b64encode`, `urlsafe_b64encode`,
  `b32encode`, `b32hexencode`, `b16encode`, `a85encode`, `b85encode`,
  `z85encode`) accept bytes-like input only: a `str` or an `int` raises
  `TypeError`.
- Decoders (`b64decode`, `standard_b64decode`, `urlsafe_b64decode`,
  `b32decode`, `b32hexdecode`, `b16decode`, `a85decode`, `b85decode`,
  `z85decode`) accept bytes-like input or a `str`. A `str` is encoded as
  ASCII; a `str` with a non-ASCII character raises `ValueError`. Other
  types (an `int`) raise `TypeError`. The `altchars` argument of
  `b64decode` and the `map01` argument of `b32decode` follow the same rule
  (`str` or bytes).
- `encodebytes` and `decodebytes` accept bytes-like input only (a `str`
  raises `TypeError`).

## Base64

Alphabet `A-Z a-z 0-9 + /`, pad `=`, as in RFC 4648.

- `b64encode(s)`: standard encoding with `=` padding, no newlines. With
  `altchars` (a 2-byte `bytes`), `+` and `/` in the output are replaced by
  its two bytes. `standard_b64encode(s)` is `b64encode(s)`;
  `urlsafe_b64encode(s)` uses `-` and `_` instead of `+` and `/`.
- `b64decode(s, altchars=None, validate=False)`: if `altchars` is given,
  its two characters are first translated to `+` and `/` in the input (an
  original `+` or `/` stays valid). Then the input is decoded by the
  rules below, non-strict when `validate` is false and strict when it is
  true. `standard_b64decode(s)` is `b64decode(s)`. `urlsafe_b64decode(s)`
  translates `-` to `+` and `_` to `/`, then decodes non-strictly (so
  `+` and `/` are accepted too).
- `encodebytes(s)`: the input is cut into chunks of 57 bytes; each chunk
  is base64-encoded and followed by `\n` (so lines of at most 76
  characters, the last one possibly shorter). Empty input gives `b''`.
- `decodebytes(s)`: non-strict decoding.

Decoding walks the input keeping a position in the current 4-character
group (0-3) and a count of pad characters seen since the last data
character:

- A data character (alphabet member) fills the next position of the group;
  each group of four produces three bytes, a group of two or three
  characters produces one or two bytes at the end (leftover low bits are
  dropped, so non-canonical endings such as `YR==` are accepted). A data
  character resets the pad count to 0.
- Non-strict mode: characters outside the alphabet and `=` are skipped.
  A `=` counts as padding only when the group has two or three data
  characters; a `=` at position 0 or 1 is ignored. At the end of input:
  a group holding one data character raises `Error`; a group holding two
  or three characters is accepted only if enough `=` were counted after
  its last data character (2 after two characters, 1 after three);
  otherwise `Error` ("Incorrect padding"). More `=` than needed is fine.
- Strict mode (`validate=True`) raises `Error` when: the input starts with
  `=`; a `=` appears at position 0 of a group; any character outside the
  alphabet and `=` appears (including whitespace); a data character
  appears after a `=`; anything follows the `=` that completed the final
  group; or at the end the group is incomplete as in non-strict mode.
  Empty input decodes to `b''` in both modes.

## Base32

- `b32encode(s)`: RFC 4648 alphabet `A-Z 2-7`. Input is processed in
  5-byte groups giving 8 characters; a final partial group of 1, 2, 3 or 4
  bytes is zero-filled and the output ends with 6, 4, 3 or 1 `=`.
- `b32decode(s, casefold=False, map01=None)`:
  1. If the length is not a multiple of 8, raise `Error`.
  2. If `map01` is given (a 1-character `str` or bytes), the digit `0` is
     replaced by `O` and `1` by that character. Then, if `casefold` is
     true, the input is uppercased (so a lowercase `map01` works only
     together with `casefold`).
  3. Trailing `=` are stripped and counted. Every remaining character must
     be in the alphabet, else `Error` (so `=` in the middle, whitespace,
     lowercase without `casefold`, `0`/`1` without `map01` are errors).
  4. The number of pad characters must be 0, 1, 3, 4 or 6, else `Error`
     (so `========` and `M=======` are errors).
  5. Each 8 characters give 5 bytes; with padding, the last group gives
     4, 3, 2 or 1 bytes for 1, 3, 4 or 6 pad characters (leftover bits
     are dropped without checking).
- `b32hexencode` / `b32hexdecode(s, casefold=False)`: the same with the
  "extended hex" alphabet `0-9 A-V`, and no `map01`.

## Base16

- `b16encode(s)`: uppercase hex.
- `b16decode(s, casefold=False)`: with `casefold` the input is uppercased
  first. Any character other than `0-9 A-F` raises `Error`; an odd length
  raises `Error`.

## Ascii85 and Base85

Both encode 4-byte big-endian words as 5 base-85 digits (most significant
first). The input is zero-padded to a multiple of 4; unless `pad` is true,
as many characters as padding bytes were added are dropped from the end of
the output.

- `a85encode`: digits are the characters `!` (33) to `u` (117). An
  all-zero word becomes `z` (except the final, padded word when `pad` is
  false: it is written as `!!!!!` and then truncated). With `foldspaces`
  a word of four spaces becomes `y`. With `adobe` the result is framed as
  `<~` + data + `~>`. With `wrapcol` > 0 (raised to 2 if `adobe` is true
  and it is smaller): the text after adding `<~` (but before `~>`) is cut
  into lines of `wrapcol` characters joined with `\n`; with `adobe`, if
  the last line plus 2 would be longer than `wrapcol`, an empty line is
  added; then `~>` is appended.
- `a85decode`: with `adobe`, the input must end with `~>`, else
  `ValueError`; that is removed, and a leading `<~` too if present. Then,
  processing the input followed by four `u` characters: characters `!` to
  `u` are collected into groups of 5 and each group gives a 4-byte word; a
  group whose value exceeds 2**32 - 1 raises `ValueError`. `z` outside a
  group gives four zero bytes and inside a partial group raises
  `ValueError`; with `foldspaces`, `y` likewise gives four spaces (and is
  an error inside a group; without `foldspaces` `y` is an invalid
  character). Characters in `ignorechars` (a `bytes`) are skipped; any
  other character raises `ValueError`. The checks run in that order, so a
  character in the `!`..`u` digit range (and `z`, and `y` with
  `foldspaces`) is always decoded as data and never skipped, even when it
  is listed in `ignorechars`. Because of the four added `u`s, a
  final partial group of `r` characters (2 <= r <= 4) is completed with
  `u` and gives its first `r - 1` bytes; a final group of a single
  character is completed with `u`s too (and overflow-checked like any
  group, so a lone trailing `u` raises `ValueError`) but gives no bytes.
- `b85encode(b, pad=False)`: digits from the alphabet
  `0-9 A-Z a-z !#$%&()*+-;<=>?@^_`{|}~` (in that order), no `z`/`y`
  shortcuts.
- `b85decode(b)`: the input is padded with `~` to a multiple of 5, each
  group of 5 gives a word, and the bytes for the padding are removed from
  the end. A character outside the alphabet raises `ValueError`, and a
  group above 2**32 - 1 (the padded last group included) raises
  `ValueError`.
- `z85encode(s)`: `b85encode(s)` with each character mapped to the Z85
  alphabet `0-9 a-z A-Z .-:+=^!/*?&<>()[]{}@%$#` (position for position).
  Partial final groups are allowed, as in `b85encode`.
- `z85decode(s)`: the inverse mapping, then `b85decode` rules (bad
  characters and overflow raise `ValueError`).

## Errors

Only the exception kind is compared: `Error` (the module's own class,
compared with `binascii.Error`), plain `ValueError`, and `TypeError`. The
base64, base32 and base16 decoders raise `Error` for bad data; the
Ascii85, Base85 and Z85 decoders raise plain `ValueError`; a non-ASCII
`str` argument raises plain `ValueError` in every decoder.

## Never tested

`altchars` or `map01` of the wrong length (an `AssertionError` in
`base64`); a `str` `altchars` in `b64encode`; a `str` `ignorechars`;
memoryviews of non-byte formats or more than one dimension; the legacy
`encode`/`decode` file functions and the command-line interface; in
non-strict base64 decoding, a data character after a `=` that completed a
group (for example `YWI=YQ==`; its result changed between 3.13 releases);
error messages.
